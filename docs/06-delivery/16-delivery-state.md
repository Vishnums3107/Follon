# Delivery state — the resume-here document

**This is the one file to read first in any new session, in any tool.** It answers
three questions and nothing else: what is verifiably true right now, what is
genuinely left, and what the next concrete action is.

It is deliberately separate from
[`14-master-plan-conformance-audit.md`](14-master-plan-conformance-audit.md),
which is the permanent requirement-to-evidence record and keeps growing. This
document is short, current, and rewritten as work lands.

## How to resume

```bash
git -C . status --short           # what the previous session left uncommitted
python tools/session_status.py    # re-measure every suite, rewrite the block below
```

`tools/session_status.py` runs each suite as a real subprocess and records the
process's own exit code. It never infers a result from a pipe's status — a
mistake this repository has already been bitten by once (conformance-audit item
40). Anything in the generated block was measured; anything outside it is prose
a human or an agent wrote and is a claim until re-measured.

## Working rules for any session on this repository

These are not style preferences. Each one exists because violating it has
already produced a real defect here.

1. **No synthetic data presented as evidence.** A fixture lives in
   `tests/fixtures/`. `var/` is for artifacts a real computation produced. A
   dashboard panel with no real backing renders its empty state; it is never
   filled with plausible-looking numbers. (Conformance-audit items 23–24 and 45
   are both remediations of exactly this.)
2. **Capture exit codes directly, never through a pipe.** `cmd > log 2>&1; echo $?`
   — then read the log. `cmd | grep error` returns grep's status, not the
   command's, and has already masked a broken build here.
3. **Do not record a status you did not measure.** Re-run
   `python tools/session_status.py` before writing any claim about suite health.
4. **Land slices whole, never half.** A multi-session epic is cut into slices
   that each compile, test, and stand alone. The previous session's refusal to
   half-land the 5.6 combo epic is why it is still open and still clean.
5. **Every behavioural change carries a test that fails without it.** Where a
   property test is added, verify it catches a deliberately injected defect
   before relying on it (the method used for items 42–44).
6. **Money is fixed-point `Decimal`.** Never `f64`, anywhere on a value path.
7. **Broker credentials never reach strategy code**, and the desktop never
   contacts a broker directly — it submits a validated request to the Risk/OMS
   route, which is the sole submission authority.

## The backlog that code can actually close

Ordered by the sequence recommended below, not by size. "Slices" are

### E1 — Risk-gated multi-leg combo order path (conformance row 5.6)

The largest genuinely-bounded engineering gap in the repository, and the one
the previous session explicitly declined to half-land.

**What exists.** `core/execution::plan_option_combo` is a real, tested
fixed-point planner. `PaperBrokerAdapter::submit_combo` rejects by default;
`IbkrControlledLiveAdapter` and the PAPER IBKR bridge override it with a real
atomic BAG transport. The gRPC service exposes combo *planning*.

**What is missing.** `PaperBrokerRegistry::submit_combo` is reached from no
real order flow — it calls `request.validate()` and forwards straight to the
adapter, bypassing `evaluate_risk`, kill switches, self-trade and rate limits,
`OmsOrder` lifecycle, and the journal. A repository-wide search finds no caller
outside `core/paper` itself. `core/live` has no combo type or method at all.

| Slice | Scope | State |
| --- | --- | --- |
| E1.1 | `ComboIntent`, `ComboIntentLeg` and `ComboPriceLimit` in `core/domain`, with validation, exact net-price and gross-notional arithmetic, and per-leg position projection. `core/execution` now re-exports the price-limit contract instead of defining its own, so the planner and the risk gate cannot disagree. | **done** 2026-09-23 |
| E1.2 | Aggregate risk evaluation for a combo in the paper risk gate: gross notional against the order-notional limit, per-leg price collar against each leg's mark, projected position per instrument, self-trade across all legs, cash reservation for the net debit | next |
| E1.3 | Risk-gated `submit_combo_intent` in `core/paper`: kill switches, OMS lifecycle for the combination as one order, durable per-combo journal record, restart recovery | open |
| E1.4 | `core/live` parity for the same path | open |
| E1.5 | Desktop/gRPC surface for the risk-gated path, replacing planning-only exposure | open |

**E1.1 design decisions a later slice must not silently reverse.** Each is
covered by a test named after it.

- **A combination is never decomposed into independently marketable legs.** The
  adapter either executes every leg atomically or rejects before transmitting
  any of them. This is why the risk gate assesses the combination as one
  economic unit and the OMS will track it as one order.
- **One leg is refused.** A single-leg "combination" is a plain order, and the
  plain-order path carries strictly more risk coverage, so it must not be
  reachable through `ComboIntent`.
- **Duplicate instruments are refused, not netted.** Netting would change the
  economics the operator approved and would defeat the per-instrument position
  projection the risk gate performs.
- **`gross_notional` sums leg magnitudes; it does not net them.** On the test's
  vertical spread that is 50, where a net-price view reports 10. The short leg
  is a real obligation until the combination is closed, so an aggregate limit
  has to see it. Netting here was injected as a deliberate defect and the test
  caught it.
- **A maximum-debit protection refuses a combination that prices to a credit**,
  even though a credit is "cheaper" than any debit cap, and vice versa. The
  operator approved a debit structure; a credit one is a different trade.
  Removing the sign guard was injected as a deliberate defect and the test
  caught it.

## The backlog that code cannot close

No amount of engineering moves these. They are the reason the audit's
[business-readiness decision](14-master-plan-conformance-audit.md#business-readiness-decision)
reads **not approved for capital-bearing or customer-facing production use**.

| Gate | Required | Progress |
| --- | --- | --- |
| PAPER reliability | 30 clean real PAPER sessions, no unexplained discrepancy | 0/30 |
| Controlled LIVE | 60 clean small-capital sessions after reviewed approval | 0/60 |
| Operator usability | 5 design partners completing workflows unaided | 0/5 |
| Options acceptance | 1 independently verified option-capable broker export reconciled across BACKTEST/PAPER/LIVE | 0/1 |
| Commercial | 10 paying professionals or 3 paying organisations | 0/10, 0/3 |
| Security | Independent penetration test of the exact deployment, plus remediation | not started |
| Legal/compliance | Entity, contracts, terms, market-data licences, broker permissions, regional and tax review | not started |
| Production operations | Named on-call owner, monitoring, TLS, secret custody, backups, restore/DR drills | mechanisms built, never drilled externally |
| Release supply chain | Controlled signer, SBOM review, vulnerability disposition, independent promotion | mechanisms built, no independent promoter |

Two gates deserve calling out because they are cheap and currently at zero:
the **30 PAPER sessions** need only a configured IBKR paper account and elapsed
time, and they are the single highest-signal validation available. The
**options acceptance** gate is what E1 is a prerequisite for.
